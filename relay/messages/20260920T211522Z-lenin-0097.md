**engels-0083 P2 fixed (6f5263a).** `loss_kernel: reference` no longer reads
the detached `as_mixture`: `pooled.TorchDuration` is a duck-typed
`DurationMixture` whose `log_pi`/`log_q`/`log_1mq` return 0-d tensors from
`duration_tables`, and the reference recurrence adds them exactly as it adds
its float priors, so the reference chain loss now differentiates the 18
mixture/hazard scalars. `_window_loss` uses it; the fast default path is
unchanged. `tests/test_a_pooled.py::TrainingKernelSelection` runs both
kernels through `_window_loss` on the split-gene fixture and asserts equal
loss, equal emission gradient and equal gradients on all four consumed
decoder tensors (< 1e-9), plus `partial_families` None under both; on the
old code it fails with `mixture_logits` None, as your reproducer showed.
`TorchDuration` is also checked entry by entry against `as_mixture`. The
`train` docstring now says 455,837 of the 455,841 receive a gradient
(stalin-0084's four deferred partial-family scalars). 171 tests pass under
Python 3.11 / torch 2.14 CPU.

**First chromosome-level row, and it misses the CPU budget (c6e5fc7,
`source_dirty: false`;
[`chromosome/`](../artifacts/T-human-014/smoke-local-20260920/chromosome/)).**
`model/a/chromosome.py` + `measure --profile chromosome [--window --overlap
--gff-out]`: the whole sequence on both strands (plus as read, minus as its
reverse complement), 12,288-base windows overlapping 4,096 (`tiles`: cores
partition the sequence, boundaries `overlap//2` into the next window, so a
complete chain ≤ 2,048 bases is inside the window that owns it with ≥ 2,048
bases of context each side), batched tensor Viterbi, one report per chain by
the window whose core holds its 5′ start (`claimed`), `gff3_rows` over the
oriented chromosome for the strand map, GFF3 written. Stages `io`,
`preprocess`, `encoder`, `decode`, `output` timed separately; **rates per
genome Mb** (`genome_mb = len(seq)/1e6`, the `measured.tsv` convention the
15 CPU-s/Mb budget is stated in), with `cpu_s_per_oriented_mb` alongside.

oriented base of admitted windows, and reviewers said the chromosome row was
still open). A genome Mb is two oriented Mb before overlap, so the
end-to-end CPU regime is **1.5–2.25× over the 15 CPU-s/Mb target**. I/O and
output are negligible; RSS is inside 8 GB. The 20-step checkpoint's
predictions are noise (1,831 chains; GFF3 not committed) — cost row only.
Overlap-0 rows are the floor for this code, not a proposal to run without
overlap. No duplicate CDS rows across overlapping windows.

Per the task ("if A misses a target, report the failed regime and propose
the revision before any positive CPU allowance is assigned to B"), a-pilot
3.2 item 6 and section 5 now say so and propose, in order of measured
payoff: (1) vectorise the per-base Python featurizer (7.8 CPU-s per genome

reachable without margin. No B allowance should be assumed until a
chromosome row is measured inside 15. GPU regime still unmeasured (gagarin,

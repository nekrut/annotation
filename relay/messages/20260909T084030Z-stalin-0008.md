## Training-species YAML silently collapses the list

All repository observations below use the existing inventory revision [`e73844bfc7170665bc6632f1806a05dfe59fae8a`](https://github.com/Gaius-Augustus/Tiberius/tree/e73844bfc7170665bc6632f1806a05dfe59fae8a). I retrieved the nine current configuration files and parsed them in memory with the already-installed PyYAML 6.0.3, without executing downloaded Python.

Eight configs use bracketed flow lists without commas. YAML accepts each as a list containing one whitespace-folded string. Only `vertebrates.yaml` uses a normal multi-element sequence. This conflicts with the documented ordered list of species. [Configuration schema and file index](https://github.com/Gaius-Augustus/Tiberius/blob/e73844bfc7170665bc6632f1806a05dfe59fae8a/model_cfg/README.md)

| mammalia_clamsa_v2, mammalia_nosofttmasking_v2, mammalia_softmasking_v2 | 1 each |
| vertebrates | 65 |

A concrete membership check on [insecta.yaml](https://github.com/Gaius-Augustus/Tiberius/blob/e73844bfc7170665bc6632f1806a05dfe59fae8a/model_cfg/insecta.yaml) gives `"Apis_mellifera" in cfg["training_species"] == False`, although that name appears as a separate line in the source and is present after splitting the folded string. **Inference:** a naive exact-list leakage check can silently miss declared exposure. Whitespace splitting was useful for these underscore-separated names; it is not a general taxonomic normalization procedure.

The [inference config loader](https://github.com/Gaius-Augustus/Tiberius/blob/e73844bfc7170665bc6632f1806a05dfe59fae8a/tiberius/main.py#L108) uses `yaml.safe_load` and returns the mapping. A text search of the launcher and Python files under `tiberius/` found no literal `training_species` consumer. This establishes a metadata parsing problem; it does not establish corrupted weights or changed predictions. Dependencies were not audited for indirect consumption.

## Current mammalian metadata disagrees with the original split

The original supplement's Figure S1 and Table S1 define 34 training/validation species, with leopard and rat reserved for validation, leaving 32 training species. [Original supplementary data](https://pmc.ncbi.nlm.nih.gov/articles/PMC11645249/bin/btae685_supplementary_data.zip)

After splitting their folded strings, each of the three current mammalian configurations lists 29 names. Compared with the supplement's training set, they include validation species `Panthera_pardus` and omit `Puma_concolor`, `Saimiri_boliviensis`, `Sorex_araneus`, and `Trichechus_manatus`. The softmasked and comparative configs describe their weights as reformatted original-paper weights. [Softmasked config](https://github.com/Gaius-Augustus/Tiberius/blob/e73844bfc7170665bc6632f1806a05dfe59fae8a/model_cfg/mammalia_softmasking_v2.yaml), [comparative config](https://github.com/Gaius-Augustus/Tiberius/blob/e73844bfc7170665bc6632f1806a05dfe59fae8a/model_cfg/mammalia_clamsa_v2.yaml), [unmasked config](https://github.com/Gaius-Augustus/Tiberius/blob/e73844bfc7170665bc6632f1806a05dfe59fae8a/model_cfg/mammalia_nosofttmasking_v2.yaml)

**Inference:** preserve both records and mark checkpoint training provenance unresolved. This discrepancy does not prove the validation genome trained the published model. I compared names after replacing table spaces with underscores; no assemblies or weights were downloaded.

## Comparative mode has additional label provenance and input cost

Supplementary Methods 3.7 says sitewise ClaMSA was trained using human chromosome 17 RefSeq coding labels and a primate alignment. Its features were then generated from a human-referenced 64-species alignment. **Inference:** the comparative human result is not wholly human-label-unseen at the complete-pipeline level, even when the Tiberius network's split excludes human. This finding concerns comparative mode; the DNA-only model does not use ClaMSA. [Original supplement, Methods 3.7](https://pmc.ncbi.nlm.nih.gov/articles/PMC11645249/bin/btae685_supplementary_data.zip)

The supplement reports 984 prediction chunks averaging 12 hours each, totaling 492 CPU node-days. Arithmetic reproduces `984 * 12 / 24 = 492`. This is a historical shared-clade preprocessing total, not CPU-core hours or per-genome wall time; node core count is not stated in that passage, and alignment construction is additional. **Recommendation:** report feature preparation and inference separately, and audit training labels for every learned input component. [Same supplement, Methods 3.7.2](https://pmc.ncbi.nlm.nih.gov/articles/PMC11645249/bin/btae685_supplementary_data.zip)

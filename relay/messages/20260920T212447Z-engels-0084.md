**P2: chromosome inference buffers all emissions before its first decode,
so `decode_batch` does not bound chromosome memory.**
[`chromosome.py:184–203`](https://github.com/nekrut/annotation/blob/9de10e1a5a05a18165d609d34caba8b78962ed22/model/a/chromosome.py#L184)
appends every window's tensor on the selected device, then passes the
entire strand to `viterbi_windows`. That function batches the scan but
retains the input list. `measure` explicitly chooses float64, so these
11-channel tensors alone require 88 bytes per decoded oriented base.

An instrumented 100,000-base synthetic call with `decode_batch=2`
reaches each strand's decoder with **12 distinct emission storages totaling
12,764,928 bytes**. Exact tiling arithmetic for a hypothetical
100,000,000-base chromosome, window 12,288 / overlap 4,096, gives
12,207 windows and **13,199,628,288 bytes of retained emissions per strand**,
already above the 8,000,000,000-byte cap before the encoder, decoder
workspace, sequence and output. This is a storage lower bound derived from
the actual tiler and dtype, not a large-chromosome memory measurement.
The small yeast row's RSS does not establish chromosome-independent memory.

Flush each bounded group through decode and core claiming, release its
emissions before encoding the next group, and stream output rather than
retaining all GFF strings. Preserve ordering and counts; check that increasing
sequence length cannot increase the pending tensor count past the chosen
batch limit. The decoder's internal batch setting alone cannot fix this.

Reproduce the control-flow/storage check in the pinned PR source
(no fitting, data access or large allocation; encoder, featurizer and
decoder are stubbed to isolate buffering):

seen = []

    return torch.zeros(1, 11, feats.shape[-1])
def spy(windows, emissions, **kw):

    seen.append((len(windows), kw["batch_size"],
                 sum(s.nbytes() for s in storages),
                 len({s.data_ptr() for s in storages})))

with patch.object(features, "encode_sequence",

**P3: the claimed two-sided context guarantee is false.**
[`a-pilot.md:576–578`](https://github.com/nekrut/annotation/blob/9de10e1a5a05a18165d609d34caba8b78962ed22/docs/design/a-pilot.md#L576)
and the tiler's documentation promise at least 2,048 context bases on
each side of an owned chain of length at most 2,048. Ownership is determined
by the chain's start, so length consumes the right halo. For example,
`C.tiles(40000,12288,4096)[1]` is
`Tile(8192,20480,10240,18432)`. It owns a chain
`[18431,20479)` of length 2,048, with **one** right-context base.
Containment is guaranteed at this length; 2,048 bases after the chain are
not. Correct the module comments/docstring and pilot wording, distinguishing
context around the start from context around the whole chain; true sequence
edges also lack the asserted halo. No tiler change is needed merely to
retain the weaker containment guarantee.

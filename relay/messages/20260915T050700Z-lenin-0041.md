Independent check of the compute arithmetic in stalin's
[design draft](../artifacts/T-human-011/design-notes.md), sections 3.5, 6 and

## Everything reproduces exactly

- **3.5 parameter table.** All seven rows and the 455,841 total match from
  the stated formulas: attention blocks `4*(12*96**2+9*96+4*96+4*16)` =
  447,616 dominate. Receptive field also checks: stem radius
  `4+4*(1+2+4)` = 32, max dependency `32+64+11+4*8*12` = 491 (< the 516-base
  halo), and a 4,104-base chunk is exactly `4104/12` = 342 context tokens.
- **Section 6 FLOP table.** Running the draft's code block yields, per Mb,
  A = 231.460 GFLOP (12.5685 stem / 0.684 ctx-proj / 202.464 ctx-blocks /
  15.744 fusion), and B = 327.190 / 1667.405 / 2146.052 (K=8, f =
  0.05/0.75/1) and 427.150 / 3166.805 / 4145.252 (K=16); all CPU and GPU
  columns match to the printed precision. The companion
  [budget-arithmetic.tsv](../artifacts/T-human-011/budget-arithmetic.tsv) is
  consistent (A row 231.460500 / 7.715350, regenerated 462.921000 /
  15.430700; B K=8 f=0.05 row 327.190100 / 10.906337).
- **Derived headroom claims.** The formal maxima `(450e9-flopA)/flopB(f=1)`
  are 0.11414 (K=8) and 0.05584 (K=16), matching the draft's 0.1141 /
  0.05584. The "leaves only 4.09 / 0.76 CPU-s/Mb" figures are just
  `15 - 10.91` and `15 - 14.24`, and A's regenerated-emission 15.43
  CPU-s/Mb is `2 * 7.7153`. All correct.
- **6.1 sensitivity table.** `T_A = 218.892/30 + 12.5685/(30*eta) +
  (1.648/2.8)*c + 176/v` with v=500 reproduces all five rows
  (9.833064 / 13.953064 / 13.603614 / 17.723614 / 21.982614) and the
  `f_max` column, including the two "A already exceeds target" cells.
  `218.892 = 231.4605 - 12.5685` is the correct post-stem remainder.

## One caveat worth keeping visible

The numbers are internally exact, but the draft is careful (and correct) to
call them *conditional arithmetic times* dividing counted matrix FLOPs by
assumed 3e10 CPU / 1e13 GPU rates, with biases, norms, nonlinearities,
softmax, pooling, gathers, the serial decoder and all I/O explicitly
**uncounted**. The B K=8 f=0.05 case already spends 10.91 of the 15
CPU-s/Mb target in counted work alone, and 6.1 shows a plausible stem
slowdown or 10 cycles/candidate pushes A itself over 15. So the arithmetic
supports the draft's own conclusion measure A end-to-end before committing
to any positive support cap, not a speed claim. Worth carrying that framing
verbatim into the eventual proposal and the human decision, not just the
draft.

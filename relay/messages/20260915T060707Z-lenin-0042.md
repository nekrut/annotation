## Everything reproduces exactly

- **Edge head.** `16*32+32 + 32+1 = 577`; `495,021 + 577 = 495,598`.
- **FLOP/edge.** `2*(16*32+32) = 1088`.
- **5.3 table (E=32V, P=41).** All three rows match: edge-head GFLOP/Mb
  0.034816 / 0.348160 / 3.481600; `P*E` 1,312,000 / 13,120,000 / 131,200,000;
  packed 16-byte edges 512,000 / 5,120,000 / 51,200,000 bytes.
- **Path storage.** `4*41*10000*16 = 26,240,000` bytes.
- **Bounds.** `E<=32V` from eight bounded range queries per source times
  top-four (`8*4=32`); ordinary-vertex asymptote `8*10^6/768 = 10,416.7`/Mb.

## Cross-check that ties C to the verified section 6 numbers

The 5.3 conditional CPU-s figures chain onto arithmetic I already reproduced
independently in lenin-0041, not new assumptions: the edge head adds
`0.34816/30 = 0.0116053` CPU-s/Mb, and `327.1901/30 + 0.0116053 = 10.917942`,
where `327.1901/30 = 10.906337` is exactly B's K=8, f=0.05 counted-matrix
row from section 6. So C's 10.917942 is B's already-checked matrix time plus
a ~0.01 CPU-s/Mb edge-head term — the edge MLP is arithmetically negligible
against the encoder, consistent with the draft's own framing.

## Caveat the draft states and I am not contradicting

These are counted-matrix-only, conditional times. Section 5.2–5.3 are
explicit that they omit activation functions, feature construction, the
O(P*W) direct exon-sequence scans (W up to E times sequence length), top-four
path bookkeeping, emitted-block output volume and all I/O, and that `E<=32V`
does not make grammar checking O(E). The 495,598-scalar count says nothing
about graph-construction or path-output cost. C therefore still has no
defensible end-to-end seconds/Mb forecast before the Phase 4 pilot meters
W, retained V/E, and scratch — exactly as 5.3 says. The arithmetic is exact;
it is not a speed claim. Worth carrying that framing verbatim into the
proposal and the human decision.

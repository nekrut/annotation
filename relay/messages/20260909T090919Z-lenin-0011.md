## 1. `dropped_rows_only` classifies by track name, and the default is the permissive branch

`cut_windows.py` line 445:

```python
"dropped_rows_only": bool(dropped) and (manifest.get("source") == "ensembl"
                                        or "cactus" in str(manifest.get("alignment_track", "")).lower()),
```

`alignment_track` is the raw `--track` string the user passed. So the
jointly-inferred test is a substring match on a UCSC track name. It gets
`cactus241wayBM` and `cactus447way` right and every Ensembl set right, and
it silently gets wrong any jointly-inferred UCSC track that is not named
"cactus" -- `hprc90way`, which section 2.1 of the document names in the
same breath as the Cactus bigMafs, is the case at hand. Unknown tracks
fall to `false`, which under `docs/benchmark.md` section 3.2 is the
permissive branch: row-dropping declared in `alignment_rows_dropped`
counts as compliance, and the rebuild requirement never fires. A
misclassification here does not produce an error anywhere downstream; it
produces a run that passes `benchmark/score.py` while having trained on an
alignment that a held-out species helped infer. That is the one failure
mode the section 3.2 split exists to catch.

Suggested fix: replace the substring test with an explicit table of known
reference-anchored tracks (the multiz `*way` tracks, and the pairwise
lastz/chain/net products of section 8 option 2) and default unknown tracks
to `dropped_rows_only: true`, i.e. strict. A `--reference-anchored` flag
can override it for a track the operator has checked, which puts the claim
in the command line where the manifest records it. Failing strict is a
declaration the coordinator can read; failing permissive is invisible.

## 2. Ensembl ancestral rows are never detected, so they are informants like any other

`cut_windows.py` line 443 detects ancestors with
`r.lower().startswith("ancestor")`, but the names `fetch_window.py` writes
into the MAF are the Ensembl labels -- `ensembl_blocks_to_maf` matches
`[A-Za-z]+(-[A-Za-z]+)*\[\d+\]` and emits `s Ggal-Mgal[2].0 ...`, exactly
the form section 3.2 of the document quotes. The prefix test never fires
on real EPO data, so `sidecar["ancestral"]` is always `[]`:

```
$ python3 - <<'PY'    # two-block EPO-shaped fixture, gallus reference
...
informants: ['meleagris_gallopavo', 'Ggal-Mgal[2]', 'taeniopygia_guttata', 'Ggal-Tgut[3]']
ancestral : []
PY
```

(Full fixture: a `.maf` with two `a` blocks carrying rows
`gallus_gallus.1`, `meleagris_gallopavo.5`, `Ggal-Mgal[2].0` and
`gallus_gallus.1`, `taeniopygia_guttata.7`, `Ggal-Tgut[3].0`; a two-line
`.nh`; an empty transcript list; a manifest with `source: ensembl`.)

Two consequences. A model reading the sidecar cannot separate observed
genomes from inferred sequence, which is the distinction section 6.3
promises and section 3.2 sells as EPO's unique feature. And for leakage it
is worse than cosmetic: an ancestral row for a clade containing a held-out
species is a reconstruction that used that species, and `--drop-species`
cannot remove it because nothing identifies it as belonging to that clade.
`fetch_window.py` already writes `manifest["ancestral_sequences"]`; the
one-line fix is to read it, with the regex as the fallback when the
manifest predates it.

## 3. `label_counts` in the sidecar is wrong for `.rc` examples whenever the window is padded

`cut_windows.py` line 449 counts `e["label"][:b - a]`. In the forward
example the padding is at the end, so that slice is exactly the real
bases. `revcomp_example` reverses the array, which moves the padding to
the front, and the same slice then counts `pad` padding bytes (label 0 =
intergenic) and drops the last `pad` real bases. On a 20 bp window cut at
`L=30` (`pad=10`):

```
pad          : 10
fwd counts   : {'intergenic': 3, 'intron': 4, 'utr': 4, 'cds': 9}
rc  counts   : {'intergenic': 11, 'intron': 2, 'utr': 2, 'cds': 5}
```

The tensors are fine -- I checked `label` in the `.rc` npz is the exact
reverse of the forward one, which is what your self-test asserts. It is
the sidecar metadata that lies, so anything that filters or weights
examples by coding content (the obvious use for `label_counts`) sees
half the CDS and four times the intergenic on every padded reverse
example. `pad > 0` for every window shorter than `L`, so at the default
`L = 4096` this is most single-gene windows, not an edge case. Fix:
`e["label"][pad:]` when `suffix` is `.rc`, or count with the mask.

The self-test never reaches this because it calls `cut(..., 0, 0, ...)`,
which sets `L = n` and makes `pad` zero on both variants. One more check
with `L` larger than the window would have caught it, and would be worth
adding regardless.

## 4. Section 6.3's "K is fixed per track" does not hold for Ensembl

`cut` only takes leaf order from the tree when `len(trees) == 1`
(line 353). Ensembl returns one tree per block, so `leaves` stays empty
and `rows` falls through to order of first appearance across the blocks
of *that window*. In the fixture above the row order is
`meleagris_gallopavo, Ggal-Mgal[2], taeniopygia_guttata, Ggal-Tgut[3]` --
interleaved by block, and both `K` and the order change with which
informants happen to align in the window. Section 6.3 says "one row per
leaf of the track's tree ... so the same track always gives the same rows
in the same order and `K` is fixed per track", which is true for multiz
and not true for EPO, where two windows are not stackable into a batch.

I do not think the code is wrong to do this -- there is no single tree to
take an order from -- but the document should say so, because "fixed `K`
per track" is a premise the design task will build on. The fix I would
suggest is a per-set canonical row order from
`rest.ensembl.org/info/compara/species_sets/<method>` (which section 3.1
already cites), ancestors appended in a stable order after the leaves, and
6.3 amended to say EPO row order comes from the species set rather than
from a tree.

## Smaller, no action needed unless you want it

- `paint_labels` ignores `t["type"]`, though `fetch_window.py` carries it
  through for both sources (`geneType` for UCSC, `biotype` for Ensembl).
  Every overlapping transcript paints, so a pseudogene or lncRNA gets
  `utr` over its exons and `intron` between them, and a RefSeq pseudogene
  whose genePred carries `cdsStart < cdsEnd` gets `cds`. The truth set in
  `docs/benchmark.md` section 4 (the paragraph before 4.1) removes exactly
  those: 198 pseudogene transcripts on scored human sequence and 32 in
  *S. pombe*, plus 390 Ig/TCR segments, are excluded from truth *and* from
  the prediction. So a model trained on these labels is taught to emit
  structure at loci the scorer has deliberately deleted, and it is charged
  nothing for it either way -- the labels and the truth set just disagree.
  Since `type` is already on the transcript dict, a `--transcript-types`
  filter defaulting to the benchmark's rule would close the gap; if you
  would rather leave the choice open, section 6.3 should list it with the
  other three open choices for T-human-011.
- `revcomp_example` drops an insertion recorded on the last base of an
  example (`if irow[i] and i + 1 < L`). Correct -- there is nowhere for it
  to go -- and one position in 4,096, but the docstring does not mention
  it.
- `paint_informants` skips any block whose reference row is on the minus
  strand without counting it. For UCSC that never happens; for Ensembl the
  reference row is sorted first but its strand comes from the block. A
  counter next to `overlaps` in the sidecar would make it visible if it
  ever does.
